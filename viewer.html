How it works — task → robot actions
          

            
1. Scenario → spec. A (scenario, seed) is resolved into a
              scene spec (board on/off, which piece, its start square/spot, camera,
              lighting, floor) and a motion primitive — either a move
              (grasp A → place B) or a pickup (grasp → lift & hold). The seed
              drives every random choice, so an episode is fully reproducible.

            
2. Motion plan → waypoints. The primitive expands into the measured
              phase machine: home → approach → descend/grasp → lift → traverse →
              place → retract (pickups: … → lift high & hold). The
              colored spheres are those waypoints; the line is the true TCP path.

            
3. Inverse kinematics. The path is sampled at the camera rate; each
              frame the arm solves IK to put the tool tip on the path, kept vertical (J5
              holds the grip-plane / wrist-camera orientation — that's the yaw 0 vs 90).

            
4. Frames. The image is rendered at the true pose every frame
              (smooth), while the logged state is sample-held (~every 3rd frame) to
              match the real recorder — see the duplicated rows in frames.jsonl.

            
Task types today: queen_move / queen_move_yaw90
              (white-queen moves on a board, like the bulk of the real data) and
              table_pickup (pick a non-queen piece off a bare table, held long
              like the real pickups). Everything you change here is logged in the manifest.
